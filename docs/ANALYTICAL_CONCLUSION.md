# Аналитическое заключение о степени реализации процессов

Основа — принципы ISO/IEC/IEEE 828:2012, используемые в учебном задании (редакция имеет статус Inactive-Reserved). **Полное соответствие стандарту не заявляется и не доказывается.**

| Процесс | Статус | Обоснование |
|---|---|---|
| Идентификация КЕ | реализован | ID, путь, версия, SHA-256 в SQLite-реестре |
| Согласование изменений | реализован | решения хранятся отдельно (кто, когда, комментарий), повторное решение запрещено |
| Запрет неодобренных изменений | реализован | `apply` отклоняет `proposed`/`rejected`; самовольная правка файла выявляется аудитом |
| Связь запрос↔коммит↔тест | реализован | `commit_hash` проверяется в истории Git; ссылки на тесты проверяются матрицей |
| Baseline | реализован | неизменяемость триггерами БД, проверка `verify` |
| Учёт статусов | частично | нет истории переходов статусов по времени |
| Аудит | частично | формальные проверки; нет содержательного аудита |
| Управление выпуском | не реализован | только ручной Git-тег и CHANGELOG |

**Итог:** 5 из 8 процессов реализованы, 2 — частично, 1 — не реализован; условная оценка полноты ≈ 75 % (реализованный = 1, частичный = 0,5). Это оценка охвата функций инструмента, а не сертификация.

## Основные ограничения
1. Нет аутентификации и разграничения ролей: «кто принял решение» — произвольная строка.
2. Файл БД (`scmtrace.db`) можно заменить целиком; триггеры защищают только от изменений через SQL. Для реальной защиты нужна подпись baseline.
3. Проверка коммита подтверждает лишь его существование в истории, а не соответствие содержимого запросу.
4. Зелёный CI подтверждает прохождение тестов, но не соответствие стандарту.
5. Демонстрационная цепочка выполнена на одной КЕ (`README.md`); масштабирование не исследовалось.

## Что улучшить
Журнал переходов статусов, подпись baseline (GPG/HMAC), проверка diff коммита по пути КЕ, автоматизация релиза (см. `release-manager`).
