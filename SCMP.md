# План управления конфигурацией (SCMP) — scm-traceability

Основа: принципы ISO/IEC/IEEE 828:2012 (учебный контекст; соответствие стандарту не заявляется).

## 1. Область применения
Один Python-проект (этот репозиторий): исходный код `src/`, тесты `tests/`, документы `*.md`, workflow CI.

## 2. Роли
| Роль | Задачи |
|---|---|
| Разработчик | создаёт запрос на изменение, вносит изменение, привязывает коммит и тест |
| CCB (совет по изменениям) | принимает решение: одобрить / отклонить |
| Менеджер конфигурации | регистрирует КЕ, создаёт baseline, запускает аудит |
| Аудитор | проверяет отчёты и матрицу прослеживаемости |

## 3. Идентификация конфигурационных единиц (КЕ)  — правило SCMP-3
Каждая КЕ получает ID `CI-NNN`, путь, версию (SemVer) и SHA-256 содержимого; записывается в SQLite-реестр.

## 4. Согласование изменений — правило SCMP-4
Запрос `CR-NNN` проходит `proposed → approved | rejected → applied`. Применить (изменить версию и хэш КЕ в реестре) можно только `approved`. Решение хранится отдельно (кто, когда, комментарий).

## 5. Связь с Git — правило SCMP-5
Применённый запрос обязан иметь `commit_hash`, существующий в истории Git, и ссылку на тест.

## 6. Baseline — правило SCMP-6
Baseline `BL-NNN` фиксирует (КЕ, версия, SHA-256) и Git commit hash; изменение и удаление запрещены (триггеры БД). Новое состояние — новая baseline. Проверка `verify` обнаруживает изменённые и отсутствующие файлы.

## 7. Учёт статусов — правило SCMP-7
Статусы КЕ-версий и запросов хранятся в реестре; отчёт JSON сводит запросы по статусам.

## 8. Аудит — правило SCMP-8
`trace audit` проверяет: хэши КЕ совпадают с файлами; у применённых запросов есть коммит в Git, baseline и тест. Результат — отчёт JSON.

## 9. Выпуск — правило SCMP-9
Выпуск = Git-тег `vX.Y.Z` + запись в `CHANGELOG.md`; автоматизации релиза в инструменте нет (см. ограничения).

## Ограничения
Нет аутентификации ролей; реестр — один файл SQLite; аудит не оценивает содержательное качество документов.
