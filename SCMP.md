# План управления конфигурацией (SCMP) — scm-platform

Учебная основа — принципы ISO/IEC/IEEE 828 (ред. 2012, Inactive-Reserved); соответствие стандарту не заявляется.

## 1. Область применения
Платформа ведёт учёт нескольких проектов, их конфигурационных единиц (CI) и версий, запросов на изменение, baseline и релизов.

## 2. Роли
| Роль | Ответственность |
|---|---|
| Автор изменения | создаёт запрос на изменение, применяет одобренный запрос |
| Менеджер конфигурации (CCB) | принимает решение об одобрении/отклонении, утверждает baseline |
| Релиз-менеджер | регистрирует релиз на основе baseline |
| Аудитор | просматривает историю и отчёты |

## 3. Конфигурационные единицы
CI = именованный компонент проекта (исходный код модуля, документ, конфигурационный файл). Идентификатор: `проект/имя`. Каждая версия имеет номер MAJOR.MINOR.PATCH и контрольную сумму содержимого; новая версия обязана быть больше текущей.

## 4. Порядок согласования запросов на изменение
`proposed → approved | rejected → applied`. Применить запрос (создать новую версию CI) можно **только** в статусе `approved`; решение фиксирует лицо и комментарий. Отклонённый и применённый запросы повторно не обрабатываются.

## 5. Утверждение baseline
Baseline — неизменяемый (триггеры БД запрещают UPDATE/DELETE) набор «CI → версия» на момент утверждения. Имя уникально в проекте. Новое состояние фиксируется новой baseline; baseline можно сравнивать.

## 6. Учёт статусов
Каждое действие пишется в журнал `history` (время, проект, действие, детали). Отчёт `scmp report` сводит CI, запросы по статусам, baseline и релизы.

## 7. Аудит
Аудитор сверяет: каждая версия CI (кроме первой) связана с одобренным запросом; релиз ссылается на существующую baseline.

## 8. Выпуск релизов
Релиз = SemVer-номер + baseline. Номера уникальны и строго возрастают. Git-тег `vX.Y.Z` соответствует релизу; CI собирает пакет.

## Ограничения
Нет аутентификации (лицо принимающее решение — строка), нет криптографической подписи baseline, один пользователь SQLite.
